# Spoofing

alterself's `SpoofEngine` synthesises a complete, coherent browser fingerprint
for each token. Every field that Discord cross-validates across the HTTP layer
and the gateway identify payload is generated from the same seeded RNG so
nothing contradicts anything else.

---

## How identity is seeded

On construction, `SpoofEngine(token)` hashes the token:

```
seed = int(MD5(token).hexdigest(), 16)
rng  = random.Random(seed)
```

This guarantees that:
- The same token always gets the same locale, timezone, GREASE brand, and UUIDs.
- Different tokens get different identities.
- The identity is stable across restarts.

Session-scoped UUIDs (`launch_id`, `launch_signature`, `heartbeat_session_id`)
are also seeded from the token on init, but are **rotated** after each new READY
event using fresh `uuid.uuid4()` calls — matching the behaviour of a real client
that reconnects.

`installation_id` is intentionally **not** rotated; it represents the browser
installation and stays constant for the lifetime of the token.

## Chrome version resolution

```
1. GET https://versionhistory.googleapis.com/v1/chrome/platforms/win/
          channels/stable/versions/all/releases?filter=endtime=none
   → parse latest stable major
   → cache in memory for 24 h
   → persist to .cache/chrome_ver.json

2. On failure: read .cache/chrome_ver.json if it exists
3. On failure: use hardcoded fallback ("136")
```

The User-Agent is then built as:

```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36
(KHTML, like Gecko) Chrome/136.0.0.0 Safari/537.36
```

## Build number resolution

Discord's build number is embedded in a JS asset on the login page.
alterself scrapes it on startup:

```
1. GET https://discord.com/login
   → parse <script src="/assets/..."> tags
   → walk in reverse order (app chunk is last)
   → regex search for buildNumber patterns:
       buildNumber\s*[=:]\s*"?(\d{5,7})"?
       "buildNumber","(\d{5,7})"
       CLIENT_BUILD_NUMBER\s*[=:]\s*(\d{5,7})
       build_number[":\s=]+(\d{5,7})
       "(\d{6,7})"\s*,\s*"stable"
       build[_-]?num(?:ber)?\s*[=:]\s*(\d{5,7})

2. Cache result in memory for 1 h and to .cache/build_num.json
3. On failure: read disk cache
4. On failure: use hardcoded fallback (612808)
```

Force a refresh any time:
```python
bot._spoof.refresh_build()
```

## X-Super-Properties

The super-properties blob is a base64-encoded JSON object sent on every
HTTP request as `X-Super-Properties`. It must match Discord's
`getSuperProperties()` function output exactly.

Fields included:
```json
{
  "os": "Windows",
  "browser": "Chrome",
  "device": "",
  "system_locale": "en-US",
  "has_client_mods": false,
  "browser_user_agent": "Mozilla/5.0 ...",
  "browser_version": "136.0.0.0",
  "os_version": "10",
  "referrer": "",
  "referring_domain": "",
  "referrer_current": "",
  "referring_domain_current": "",
  "release_channel": "stable",
  "client_build_number": 612808,
  "client_event_source": null,
  "client_launch_id": "<uuid>",
  "launch_signature": "<uuid>",
  "client_app_state": "focused",
  "client_heartbeat_session_id": "<uuid>"
}
```

The gateway IDENTIFY `properties` block is generated by the same method
(`get_identify_props()`) and includes the additional gateway-only fields:
`is_fast_connect`, `gateway_connect_reasons`, `installation_id`.

## sec-ch-ua

Generated to match real Chrome's output. Three valid orderings observed in
Discord traffic are shuffled per session:

```
# Ordering A (most common)
"Not=A?Brand";v="99", "Chromium";v="136", "Google Chrome";v="136"

# Ordering B
"Chromium";v="136", "Not=A?Brand";v="99", "Google Chrome";v="136"

# Ordering C
"Not=A?Brand";v="99", "Google Chrome";v="136", "Chromium";v="136"
```

GREASE brand chosen from the real alphabet:
```
"Not A(Brand"    "Not)A;Brand"    "Not/A)Brand"
"Not=A?Brand"    "Not_A Brand"    " Not A;Brand"
```

## X-Context-Properties

Per-action location token, base64 JSON: `{"location": "<location string>"}`.

Injected automatically on HTTP requests. Context key → location string:

| Key | Location |
|---|---|
| `chat` | `chat_input_character_count` |
| `guild` | `guild_channel` |
| `profile` | `user_profile_modal` |
| `dm` | `dm_channel_jump` |
| `search` | `search_result` |
| `ctx_menu` | `context_menu_jump` |
| `add_friend` | `add_friend_page` |
| `join` | `accept_invite_page` |
| `settings` | `settings_page` |

## Gateway capabilities bitmask

The IDENTIFY payload includes a `capabilities` integer bitmask.
alterself sends `1734653`, which corresponds to:

```
LAZY_USER_NOTES              (1 << 0)
NO_AFFINE_USER_IDS           (1 << 1)
VERSIONED_READ_STATES        (1 << 2)
VERSIONED_USER_GUILD_SETTINGS(1 << 3)
DEDUPE_USER_OBJECTS          (1 << 4)
PRIORITIZED_READY_PAYLOAD    (1 << 5)
MULTIPLE_GUILD_EXPERIMENT_POPULATIONS (1 << 6)
NON_CHANNEL_READ_STATES      (1 << 7)
AUTH_TOKEN_REFRESH           (1 << 8)
USER_SETTINGS_PROTO          (1 << 9)
CLIENT_STATE_V2              (1 << 10)
PASSIVE_GUILD_UPDATE         (1 << 11)
AUTO_CALL_CONNECT            (1 << 17)
```

This matches the bitmask sent by an up-to-date Chrome client.

## App state tracking

alterself tracks whether the "browser window" is focused. This is reflected
in `client_app_state` inside super-properties.

```python
bot._spoof.set_state(focused=True)   # client_app_state = "focused"
bot._spoof.set_state(focused=False)  # client_app_state = "unfocused"
```

The gateway also uses this to set the QoS token.
